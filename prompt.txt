===============================================================
1. PRODUCT VISION
===============================================================

Build a compact coding-model platform whose defining feature is
QUALITY- AND BUDGET-AWARE COMPUTATION.

The system should not merely execute a fixed amount of computation
for every prompt.

Instead, it should estimate how difficult a request is, understand
the user's latency and output requirements, determine an appropriate
computation budget, and allocate supported reasoning or verification
steps accordingly.

The platform should contain:

1. A configurable model-building system.
2. A strict model-parameter accounting mechanism.
3. A fixed-context causal coding model.
4. A coding-oriented tokenizer.
5. A dedicated data preparation pipeline.
6. A training engine.
7. A learned or trainable adaptive-budget controller where supported.
8. An inference-time budget scheduler.
9. A custom inference runtime.
10. Hardware-specific execution backends.
11. An OpenAI-compatible HTTP API.
12. A continuous-batching scheduler.
13. A monitoring and diagnostics system.
14. Reliable checkpoints and model artifact management.
15. Automated tests and benchmark tools.

The design should allow the model, budget controller, and inference
engine to evolve independently without breaking the integration
contract.

Do not claim that a small model can match frontier coding models
without experimental evidence. Build the mechanisms needed to improve
quality per unit of computation, then measure whether they work.

===============================================================
2. GLOBAL HARD CONSTRAINTS
===============================================================

CONTEXT LENGTH:

    CONTEXT_LENGTH = 1024

The context length is permanently hardcoded to exactly 1,024 tokens.

This restriction applies to:

- Model architecture.
- Training sequences.
- Token packing.
- Positional embeddings or positional encoding.
- Attention masks.
- Inference requests.
- Conversation history.
- Prompt construction.
- API validation.
- Scheduler admission.
- KV-cache allocation.
- Evaluation.
- Model configuration.
- Checkpoint loading.
- Export metadata.
- Hardware-specific backends.

Do not implement adaptive context allocation.

Do not implement longer context tiers.

Do not expose context length as a user-configurable setting.

Do not allow configuration files, environment variables, API request
fields, dashboard controls, or hardware detection to override 1,024.

Reject or explicitly truncate inputs that exceed the supported limit.
Document the policy and preserve room for requested output tokens.

For chat requests, the prompt budget includes message boundaries,
system instructions, conversation history, tool descriptions where
applicable, and all other tokens inserted into the model input.

A request with a 900-token prompt and a requested 300-token completion
cannot be treated as though both fit into a 1,024-token total context.
Handle the distinction between prompt length and output budget correctly.

PARAMETER COUNT:

The parameter target MUST NOT be universally hardcoded.

When the user runs:

    python main.py

ask for the target number of trainable parameters.

Default:

    10M

Allow supported values such as:

    1M
    10M
    25M
    50M
    100M
    500M
    1B

Parse shorthand correctly and validate feasibility before allocation.

Construct the architecture around the chosen target.

Count all trainable parameters, including embeddings, output heads,
normalization layers, controllers, and other trainable modules.

Require the actual trainable parameter count to match the selected
target exactly. If a target cannot be achieved by a supported
architecture, explain why and offer alternatives.

Never add unused trainable parameters merely to satisfy the count.

Record the selected target and verified actual count in checkpoints,
model manifests, evaluation reports, and exported artifacts.

The parameter target is configurable. The context length is not.

TRAINING TARGET:

Default:

    200,000,000 training tokens

Allow the user to select a different target interactively.

Validation tokens must never count toward the training-token target.
Count only successfully committed training tokens.

DATASET:

Use The Stack from Hugging Face as the exclusive initial training
corpus. Do not silently add unrelated datasets or generated corpora.

TOKENIZER:

Target vocabulary:

    98,304 tokens

Use a coding-oriented BPE tokenizer unless a demonstrated technical
constraint requires a different approach.

INITIAL TRAINING ENVIRONMENT:

Google Colab with an NVIDIA T4 GPU, subject to actual runtime
availability and detected memory.

GOOGLE DRIVE:

Use Colab's built-in Python module:

    from google.colab import drive

Mount Drive using:

    drive.mount('/content/drive')

Only import google.colab on the Colab-specific execution path.
Outside Colab, use local storage and explain the limitation.

INFERENCE:

Use the custom TinyCode Inference Engine. Do not make an external
inference server a mandatory runtime dependency.

===============================================================
6. THE ADAPTIVE COMPUTATION BUDGET LAYER
===============================================================

This is a central architectural feature, not an optional cosmetic
addition.

Implement a distinct budget-control subsystem in the inference engine,
with related trainable components in the model-builder repository.

The budget layer decides how much additional computation a request
should receive within the capabilities of the actual model.

It must balance:

- Expected answer quality.
- Request difficulty.
- Output requirements.
- Latency.
- Available memory.
- Available compute.
- Queue pressure.
- Requested maximum output tokens.
- Verification requirements.
- The user's requested budget where supported.

The budget layer must not pretend to improve model capability simply
by assigning more computation. It must use supported operations and
measure whether additional computation improves outcomes.

Define an explicit request-budget object containing fields such as:

- Request identifier.
- Estimated task complexity.
- Requested latency target, if supplied.
- Requested compute budget, if supplied.
- Maximum permitted generation tokens.
- Maximum allowed internal steps.
- Verification allowance.
- Deadline.
- Memory estimate.
- Selected policy.
- Allocated budget.
- Actual consumed budget.
- Stop reason.

Use typed, validated structures.

Do not allow user-provided budgets to bypass server resource limits.

===============================================================
7. DEFINE AND IMPLEMENT THE COMPUTATION LAYERS
===============================================================

Build the following conceptual layers as explicit modules with defined
inputs, outputs, interfaces, and tests.

These layers must work together. They are not all independent neural
networks, and they do not all need trainable parameters.

LAYER 1 — REQUEST INTAKE

Accept the user's request through the API or local inference interface.

Responsibilities:

- Parse the request.
- Validate input length.
- Validate generation settings.
- Identify the task type where possible.
- Extract explicit quality, latency, and token constraints.
- Normalize the request into an internal representation.
- Preserve the original user intent.
- Reject unsupported operations safely.

Output:
A validated internal request object.

LAYER 2 — TASK AND COMPLEXITY ANALYSIS

Estimate the difficulty of the task before expensive execution.

Consider features such as:

- Input length.
- Task category.
- Number of requested subtasks.
- Whether the task requires code generation, explanation,
  transformation, debugging, or structured output.
- Whether the user explicitly requests verification.
- Available historical performance for similar task categories.
- The model's observed uncertainty signals, where available.

Start with a transparent, deterministic baseline.

Add a learned complexity estimator only when appropriate training
signals and evaluation data exist.

Do not pretend that prompt length alone measures task difficulty.

Output:
A complexity estimate, task category, and uncertainty estimate.

LAYER 3 — INITIAL BUDGET ALLOCATION

Convert the complexity estimate and request constraints into an
initial computation budget.

Consider:

- Estimated task difficulty.
- Available hardware.
- Queue pressure.
- Memory availability.
- Latency constraints.
- Maximum generation length.
- Verification requirements.

Use bounded policies such as:

- Minimal budget.
- Standard budget.
- Extended budget.
- Verification-enabled budget.

These are computation policies, not context-length tiers.

The fixed context remains 1,024 tokens in every policy.

Output:
An initial request-budget allocation.

LAYER 4 — PLANNING AND SUBTASK DECOMPOSITION

For tasks that benefit from planning, create a compact internal plan
or TODO-like sequence of actions.

Examples:

- Identify the requested result.
- Determine relevant code structures.
- Generate a candidate solution.
- Inspect possible errors.
- Verify consistency.
- Produce the final response.

The plan must be bounded by the request budget.

Do not force planning for every trivial request.

Do not generate arbitrarily long plans, and do not assume that a
longer plan necessarily improves the answer.

The planner may be rule-based initially, then improved through
measured experiments.

If an internal plan is represented as tokens for the same model,
those tokens must obey the fixed context constraints. The system
must not concatenate hidden reasoning into an input longer than
1,024 tokens.

Output:
A bounded execution plan.

LAYER 5 — MODEL EXECUTION

Execute the actual model using the selected backend.

Responsibilities:

- Tokenize the prompt.
- Validate the fixed context limit.
- Run the causal model.
- Apply supported generation settings.
- Track actual compute and token usage.
- Check cancellation and deadline conditions.
- Report backend errors to the scheduler.

Additional computation must correspond to real supported operations,
such as additional generation, an explicitly supported second pass,
or verification.

Do not simulate additional reasoning by incrementing a counter.

Output:
A candidate response and execution telemetry.

LAYER 6 — CONFIDENCE AND UNCERTAINTY ESTIMATION

Estimate uncertainty using measurable signals.

Potential signals include:

- Token probability distributions.
- Entropy.
- Agreement between genuinely independent candidate attempts.
- Calibration results.
- Task-specific validation signals.
- Known failure patterns.
- Verification outcomes.

Do not equate a high probability with factual correctness.

Do not label an uncalibrated heuristic as a reliable confidence score.

Begin with clearly named heuristic signals and document their limits.

Output:
Uncertainty estimates and evidence for whether additional work
might improve the answer.

LAYER 7 — ADAPTIVE COMPUTATION DECISION

Evaluate whether additional computation is justified.

Possible decisions:

- Accept the current candidate.
- Continue generation within the remaining budget.
- Run another supported pass.
- Invoke a configured verification stage.
- Stop because the budget is exhausted.
- Stop because the deadline is reached.
- Stop because additional work is unlikely to help.

Use explicit policy rules with bounded costs.

Where a learned policy is available, compare it against the
deterministic baseline.

Never allow indefinite loops.

Output:
A continuation decision and the updated remaining budget.

LAYER 8 — VERIFICATION

Implement optional verification appropriate to the task.

Possible techniques:

- Check output structure.
- Check whether requested sections are present.
- Validate JSON syntax.
- Validate code delimiters and formatting.
- Run safe, explicitly configured syntax checks.
- Compare candidate responses using a defined scoring method.
- Check consistency against the original request.
- Use a separately configured verifier model only when available.

Do not execute generated code on the host without an explicit,
isolated sandbox and suitable security controls.

Do not claim that a response is correct merely because it passed
a formatting check.

Output:
Verification evidence, detected errors, and a decision about
whether another attempt is justified.

LAYER 9 — BUDGET-AWARE FINALIZATION

Produce the final response when the system's stopping policy says
that additional computation is not justified or is not permitted.

Ensure the final output:

- Satisfies the request format.
- Respects the token budget.
- Preserves important details.
- Does not expose internal debugging information.
- Does not claim verification that did not occur.
- Is returned through the requested API format.

Output:
The final candidate and truthful usage metadata.

LAYER 10 — FEEDBACK AND CALIBRATION

Record useful aggregate measurements such as:

- Task category.
- Initial budget.
- Actual budget consumed.
- Latency.
- Token usage.
- Verification outcome.
- User-provided evaluation feedback where explicitly available.
- Benchmark results.
- Whether additional computation improved the outcome.

Avoid collecting sensitive request content unnecessarily.

Use this data to evaluate policy quality, calibrate uncertainty,
and improve future budget allocation.

Do not silently train on private user requests.

Any training-data collection must have an explicit, documented policy
and appropriate user consent.

Output:
Evaluation records suitable for offline policy improvement.

===============================================================
8. IMPORTANT DISTINCTION: CONTEXT, COMPUTATION, AND OUTPUT
===============================================================

The adaptive budget layer may change supported computation allocation.

It must NEVER change the 1,024-token context length.

Keep these concepts separate:

CONTEXT LENGTH:
The maximum input sequence supported by the model.

OUTPUT BUDGET:
The maximum generated tokens requested or permitted.

COMPUTATION BUDGET:
The maximum work the system may spend on a request.

VERIFICATION BUDGET:
The work allocated to supported checks or additional passes.

LATENCY BUDGET:
The deadline or response-time target.

MEMORY BUDGET:
The maximum resources a request may consume under the runtime's
admission and safety policies.

These budgets have different units and cannot be treated as
interchangeable.

A request with a larger computation budget does not automatically
receive more context or a longer output.

===============================================================
11. HARDWARE BACKEND STRATEGY
===============================================================

Implement backend detection and dispatch.

The preferred execution path depends on actual capabilities,
supported operators, memory, precision, and measured performance.

Priority:

1. CUDA when a compatible NVIDIA GPU and supported CUDA runtime exist.
2. Intel integrated graphics when a compatible, verified graphics
   execution backend is available.
3. ARM NEON when running on a compatible ARM CPU.
4. Optimized general CPU execution as the universal fallback.

This is a capability-based selection strategy, not a guarantee that
all systems support all listed backends.

A backend must advertise the operators, precisions, and features it
actually supports.

CUDA BACKEND

Implement:

- Device discovery.
- Capability detection.
- Model placement.
- GPU memory accounting.
- Supported precision selection.
- Forward-pass execution.
- Supported optimized attention.
- Synchronization.
- Memory pressure handling.
- OOM reporting and recovery.
- CPU fallback when appropriate.

Use PyTorch CUDA for initial correctness and training compatibility.
Implement native CUDA/C++ acceleration for performance-critical
inference operations when measurements justify it.

Do not require every operator to have a custom CUDA kernel.

INTEL INTEGRATED GRAPHICS BACKEND

Detect Intel integrated graphics and determine whether a supported
execution provider is installed and usable.

Investigate compatible options such as OpenVINO or another maintained
backend appropriate to the target platform.

Encapsulate the chosen provider behind the inference backend interface.

Requirements:

- Detect the actual graphics device.
- Verify that the provider can access it.
- Verify model/operator compatibility.
- Report whether execution is actually occurring on the GPU.
- Avoid claiming GPU acceleration when operations are running on CPU.
- Provide a tested fallback if the device cannot run the model.

Do not assume that PyTorch CUDA supports Intel graphics.

ARM NEON BACKEND

Detect ARM architecture and NEON support.

Implement or integrate a maintained native CPU kernel path that can
use NEON instructions where available.

Potential targets include matrix multiplication, vector operations,
normalization, and other measurable bottlenecks.

Use compile-time and runtime capability checks as appropriate.

If NEON is unavailable, use a general CPU implementation.

Do not execute unsupported ARM-specific instructions on another CPU.

CPU BACKEND

Provide a portable CPU backend on supported operating systems.

Implement:

- Correct tensor operations.
- Safe memory management.
- Thread-count configuration.
- Supported SIMD optimizations.
- Graceful fallback when optional libraries are absent.
- Correct numerical behavior.
- Model loading and inference.
- Performance measurements.

CPU-only execution must remain a first-class supported mode.

BACKEND SELECTION

At startup:

1. Discover available devices.
2. Check installed execution providers.
3. Check model compatibility.
4. Check memory availability.
5. Select a valid backend.
6. Run a small initialization or execution test.
7. Report the chosen backend and reason.
8. Fall back safely if initialization fails.

Never choose a backend solely because its name appears in a device
enumeration.
